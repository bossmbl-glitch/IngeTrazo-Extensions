# IngeTrazo Extensions — 長期開發與版本管理規範

文件版本：1.1\
建立日期：2026-11-12  
修訂日期：2026-11-16\
目標平台：IngeTrazo 0.6.0  
作業系統：Windows x64  
預設尺寸單位：cm  
介面語言：繁體中文

## 1. 專案目標

建立一套可以長期維護、持續迭代、跨電腦同步及使用 Codex 開發的 IngeTrazo 擴充套件系統。

所有外掛必須具備可追溯的原始碼、需求規格、修改紀錄、已知問題及測試結果。

## 2. 專案目錄規則

- 每款獨立外掛建立自己的管理資料夾。
- 每款外掛可以包含多個功能。
- 整合工具箱使用 `02_IntegratedTools` 管理。
- 整合工具箱內各功能使用 `features/` 子資料夾管理。
- FFD、CabinetBuilder、Lathe 等功能可以獨立記錄規格與問題。
- 不可擅自拆散現有整合工具箱的 Python 主程式。
- 目前實際原始碼以 `plugins/` 為主要來源。
- 各分類資料夾透過來源對照表指向真正的程式。
- 未完成相依性驗證前，不得任意搬動、刪除或重新命名 Python 模組及其資產。
- 所有新增外掛必須登記到總清單及來源對照表。

## 3. 新工具開發流程

當使用者提出新工具時：

1. 搜尋現有外掛及功能清單，檢查是否重複。
2. 判斷適合獨立開發或加入整合工具箱。
3. 分析 IngeTrazo API 與現有程式相容性。
4. 提供功能規格、操作方式與影響範圍。
5. 等待使用者明確要求「實作」、「開始實作」或「改給我」。
6. 直接在最新的 `develop` 分支開發，不另外建立分支。
7. 實作並執行適用測試。
8. 產生測試安裝包及修改紀錄。
9. 等待使用者實機驗收。
10. 驗收通過並取得使用者明確批准後發布正式版。
11. 正式發布後盤點其他分支，先合併需要保留的修改，再經確認刪除不需要的分支。

不得因為使用者提出需求，就自動修改原始碼。

## 4. 現有工具迭代規則

修改既有工具時，必須：

- 先讀取實際原始碼及功能規格。
- 確認修改所屬套件與功能。
- 保留其他已正常運作的功能。
- 優先進行局部修正，避免無關重構。
- 記錄修改前後的行為差異。
- 檢查是否影響相依功能。
- 更新對應功能的 CHANGELOG 和已知問題。
- 完成適用測試後才產生測試版。

不得在未確認版本來源的情況下，以舊程式覆蓋新版本。

## 5. 工具整合規則

當使用者要求把新功能加入既有工具時：

1. 確認目標工具及主程式。
2. 檢查是否存在重複入口、快捷鍵及功能。
3. 確認資產路徑、資料結構及相依模組。
4. 新增對應的功能管理子資料夾。
5. 保留整合前可以回復的版本。
6. 不得任意移除原本的獨立工具。
7. 完成整合後執行新舊功能回歸測試。
8. 經使用者確認後，才決定是否停用原獨立版。

## 6. GitHub 分支管理

### main

- 保存已確認的正式版本及歷史備份。
- 目前既有提交屬於原始備份基準，不代表所有外掛均通過實機驗收。
- 不直接在 main 進行實驗性開發。
- 正式發布前必須完成對應驗收。

### develop

- 作為日常開發整合分支。
- 保存開發中的套件分類、規格及程式修改。
- 尚未驗收的功能不得直接視為正式版。

### 直接開發與發布後清理

- 此流程適用於本儲存庫內所有子專案與外掛；使用者提出想法與需求，AI 負責開發及 GitHub 操作。
- 使用者要求開發時，直接在最新的 `develop` 分支修改、測試與提交。
- 不另建 feature、fix、dev、release 或其他臨時分支；日常開發不要求透過 PR 合併回 `develop`。
- 正式版本完成實機驗收並經使用者批准後，才將對應修改合併到 `main`、建立正式標籤及 Release。
- 每次正式發布後，必須盤點 `main`、`develop` 以外的既有分支。需要保留的修改先確認內容並合併，確認沒有遺漏後，再刪除不需要的分支。
- 不得因分支名稱看似過期就直接刪除，或丟棄尚未合併的修改；保留既有正式標籤、Release 及回復途徑。
- 每次 Git／GitHub 變更前，先說明具體動作並取得使用者確認，包括切換分支、提交、推送、PR 變更、合併及刪除分支。一次確認只涵蓋當次明確列出的動作；唯讀檢查及已要求的本地檔案修改可先進行。

### 臨時分支僅限本地（2026-11-17 修訂）

- GitHub 遠端常設分支只保留 `main`、`develop`。需要隔離開發的 `dev/`、`feature/`、`fix/`、`release/` 等臨時分支只留本地，不得推送，也不得為建立 PR 而公開。
- 禁止以 `push --all` 或 `push --mirror` 批次帶出本地臨時分支；整合與推送 `develop` 仍須取得當次明確授權。
- GitHub 不支援同一儲存庫內只讓擁有者看見某個分支。分支保護、改名及草稿皆不是隱藏機制。本地不推送也不等於工作區的存取權限保證。
- 尚未核准公開的內容，不得經由 `main`、`develop`、PR、標籤或 Release 間接發布。
- 正式發布時清查遠端臨時分支；確認修改已合併或另有可回復保存，再按當次核准範圍刪除。不可遺失其他子專案修改，保留 `main`、`develop` 與正式標籤。
- 既有遠端分支仍依儲存庫權限可見；本規則不會自動將其隱藏或刪除。刪除也不保證收回已下載副本或 PR 等引用的提交。


## 7. 版本管理規則

每款外掛維持獨立版本號，採用相容的語意化版本管理方式，並尊重既有外掛的版本制度。

版本變更建議：

- PATCH：錯誤修正及不影響相容性的調整。
- MINOR：新增相容功能。
- MAJOR：重大功能或不相容變更。

不得因為建立管理文件而擅自更改外掛實際版本號。

整合工具箱維持套件主版本，內部各功能另保存自己的修改歷史。

試用版、測試版及正式版應明確區分。

每次正式發布需保存：

- 版本編號
- 發布日期
- 修改項目
- 修正問題
- 測試結果
- 已知限制
- 安裝及回復方式
- Git Commit 或版本標籤

## 8. 測試規範

依外掛功能選擇適用測試，至少考慮：

- 一般群組及多層巢狀群組
- 不同模型比例及 cm 單位
- X/Y/Z 軸向與座標轉換
- 共面、重疊及交叉幾何
- 材質、標籤及原有物件屬性
- Undo / Redo
- 重複操作及取消操作
- 異常輸入及錯誤處理
- 舊功能回歸測試
- 安裝、啟動與相依模組載入

必須區分：

1. 靜態檢查
2. 自動化測試
3. IngeTrazo 0.6.0 實機測試
4. 使用者驗收

不能將尚未執行的測試記錄為通過。

## 9. 安裝包交付規則

每次收到明確實作要求後，應盡可能交付：

- 完整測試安裝包
- 安裝及更新說明
- 版本更新紀錄
- 測試結果
- 已知問題
- GitHub 修改紀錄或可提交的完整檔案

若無法產生安裝包，必須明確說明限制，不得宣稱已完成交付。

不得只提供無法直接安裝的零散程式碼，卻宣稱套件已完成。

## 10. GitHub 更新規則

有可用 GitHub 寫入權限時：

1. 確認目標儲存庫及最新 `develop` 分支。
2. 修改指定來源檔案。
3. 執行測試。
4. 更新對應文件。
5. 取得使用者對提交與推送的確認後，直接提交並推送到 `develop`。
6. 正式發布時，經使用者核准才合併到 `main`、建立正式標籤及 Release；發布後依第 6 節盤點與清理分支。
7. 回報 Commit、分支及同步結果。

若無寫入權限：

- 提供完整修改檔案或套件包。
- 說明 GitHub Desktop 的更新操作。
- 不得宣稱已完成雲端同步。

未經使用者核准，不得擅自發布正式版或覆蓋正式備份。

## 12. 安全及相容性

- 以 IngeTrazo 實際 API 為目標，不預設 SketchUp Ruby 相容。
- 不修改使用者模型的非指定部分。
- 不任意刪除原有材質、群組、標籤及幾何。
- 不提交密碼、憑證、API Token 或私人資料。
- 保留第三方程式的授權及著作權聲明。
- 未經使用者要求，不主動更新已安裝的外掛。
- 所有正式版本都必須有回復上一版的方式。

## 13. AI 開發助手的工作原則

ChatGPT 與 Codex 應使用同一份 GitHub 原始碼及規格。

優先閱讀：

1. AGENTS.md
2. docs/EXTENSIONS_INDEX.md
3. docs/INSTALLED_PLUGINS_AUDIT.md 或實際盤點文件
4. docs/FULL_EXTENSIONS_ORGANIZATION.md
5. 對應外掛的 SPEC.md
6. 對應外掛的 KNOWN_ISSUES.md
7. 對應原始碼

如果文件名稱或路徑已變更，應先從 Repository 核對實際位置。

開發時以最新原始碼及已驗證的測試結果為準，不能只根據歷史對話推定程式已完成。
